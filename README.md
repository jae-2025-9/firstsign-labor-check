**사인하기 전 30초, 알바 근로계약서의 빠진 항목과 불리한 조항을 기준서대로 짚어 주는 Document Agent**

## 무엇을 하나

첫 알바를 시작하는 대학생이 근로계약서 PDF를 올리면

1. **Contract Agent**가 임금, 근로시간, 휴일, 서명, 특약 같은 항목 20개를 JSON으로 뽑고
2. **Criteria Agent**가 점검 기준서(규칙 7개, 최저임금, 필수 기재사항)를 JSON으로 뽑고
3. 코드가 두 JSON과 **계산 보조값**(1일·1주 근로시간, 시급 환산, 적용 최저임금)을 PDF 한 장으로 합치면
4. **Review Agent**가 안심 / 확인 필요 / 위험 중 하나로 분류하고, 해당 규칙·법령 근거·사장님께 보낼 요청 문구를 만듭니다.
5. 마지막으로 코드가 같은 규칙으로 **교차 검증**합니다. 최종 등급은 지적한 규칙의 기준서 분류로 정하고, 에이전트와 계산이 다르면 화면에 두 쪽을 모두 보여 줍니다.

| 등급 | 기준 (점검 기준서 v2) |
|---|---|
| 위험 | 기준서에서 분류가 "위험"인 규칙(최저임금 미달, 위약금·임금 공제 조항) 중 하나라도 해당 |
| 확인 필요 | 위험 규칙은 통과, "확인 필요" 규칙(필수 기재사항, 휴게, 주휴일, 서명·교부, 다음 해 최저임금) 중 하나 이상 해당 |
| 안심 | 규칙 7개 모두 통과 |
| 판정 보류 | 시급·근로시간을 읽지 못했거나 기준서 조건이 바뀌어 판단할 수 없는 규칙이 있어 안심이라고 단정하지 않음 |

## 워크플로우

```text
근로계약서.pdf → [Contract Agent] → contract.json ─┐
                                                   ├→ [review_builder.py] → Review_Input.pdf → [Review Agent] → review_result.json
점검기준서.pdf → [Criteria Agent] → criteria.json ──┘   1부 계약 정보                                   │
                                                         2부 점검 기준                                    ▼
                                                         3부 계산 보조값 (rules.py)          [rules.py 교차 검증] → 화면
```

플레이북의 HR 예시(이력서 → 채용공고 → 매칭)와 같은 "문서 A, 문서 B, 평가 에이전트" 패턴입니다.

| 에이전트 | 입력 | 노드 | 출력 | Studio 템플릿 |
|---|---|---|---|---|
| Contract Agent | 근로계약서 PDF | Parse → Extract (20개 항목) | `contract.json` | 문서 정보 추출 |
| Criteria Agent | 점검 기준서 PDF (고정) | Parse → Extract (규칙 표 포함) | `criteria.json` | 문서 정보 추출 |
| Review Agent | 두 JSON + 계산값을 합친 PDF | Parse → Classify (3분류) → 분류별 Extract | `review_result.json` | 문서 분류 후 정보 추출 |

설정 파일은 [`agent_configs/`](agent_configs)에 있습니다. 팀 공유 압축 파일(NPOS.zip)의 설정을 학교 계정 Studio에 가져와 만든 뒤, 아래 수정 사항을 반영하고 **Studio에서 다시 내보낸 최종본**입니다.

## 실제 에이전트 실행 결과

Studio 에이전트 3개를 실제로 호출해 샘플 4종을 점검했습니다(2026-10-16). 결과는 `fixtures/live/`에 저장되어 있어 `FORCE_DEMO=1`로 그대로 재생할 수 있습니다.

| 샘플 | 평가 에이전트 | 규칙 계산 | 최종 | 보여 주는 것 |
|---|---|---|---|---|
| 1 정상 | 안심 | 안심 | **안심** | 교차 검증 일치 |
| 2 누락 | 위험 | 확인 필요 | **확인 필요** | 에이전트가 근거 규칙(모두 '확인 필요')보다 엄격하게 분류해 기준서 분류로 표시. 에이전트가 놓친 다음 해 최저임금(10,320원 < 2027년 10,700원)을 규칙 계산이 추가 |
| 3 위험 | 위험 | 위험 | **위험** | 에이전트가 놓친 휴게시간·주휴일·필수 기재사항을 규칙 계산이 채워 지적 7건 |
| 4 안심 | 안심 | 안심 | **안심** | 에이전트가 근거로 적은 서명·교부, 다음 해 최저임금은 계약서 값(양측 서명·교부 문구, 시급 10,800원 ≥ 10,700원)으로 해당하지 않아 '의견 차이'로 따로 표시 |

- 계약서 추출(Contract Agent)은 팀 예상값과 같았습니다.
- 기준서 추출(Criteria Agent)은 다음 해 최저임금 규칙의 조건·법령 근거·권장 행동 끝을 잘라 읽었습니다(표 칸이 페이지를 넘어감). 코드가 PDF 원문 표를 글자 위치로 읽어 바로잡습니다.
- 한 번 점검에 2~3분 30초가 걸립니다. 대부분 Review Agent 시간입니다(Parse → Classify → Extract). `AGENT_TIMEOUT_SECONDS` 기본값을 420초로 두었습니다.
- Studio가 가끔 `model_request_error`(분류 단계 일시 오류)를 돌려줍니다. 새 Job으로 최대 3번까지 다시 시도합니다(`AGENT_ATTEMPTS`).

## 기준서만 바꾸면 된다

중간 점검 때 남은 문제는 평가 에이전트의 분류 설명에 규칙과 금액(10,320원 등)이 직접 적혀 있어, 기준서를 바꿔도 에이전트 설명을 따로 고쳐야 한다는 점이었습니다. 이렇게 풀었습니다.

- **평가 에이전트 설명을 기준서 참조형으로**: [`agent_configs/Review Agent.json`](agent_configs/Review%20Agent.json)은 분류 설명과 결과 스키마 설명에서 금액·규칙 코드를 모두 빼고 "2부에서 분류가 '위험'인 규칙", "3부의 적용 최저임금"처럼 입력 문서를 가리키게 바꿨습니다. 팀의 v13 원본은 저장소에서 지웠고, 팀 공유 압축 파일에 그대로 있습니다.
- **숫자는 코드가 계산**: [`rules.py`](rules.py)가 기준서의 최저임금과 규칙별 분류를 읽어 근로시간·시급·적용 최저임금을 계산하고 입력 PDF 3부에 적습니다. LLM이 "주 3일 × 5시간 = 15시간" 같은 계산을 틀릴 여지를 줄입니다.
- **교차 검증**: 같은 기준서 규칙을 코드로도 판정해 에이전트 결과와 비교합니다. 둘이 다르면 두 쪽의 지적을 모두 보여 주고, 요약·권장 행동도 최종 결과에 맞춰 다시 씁니다.
- **코드가 옛 기준으로 덮어쓰지 않게**: 코드가 구현한 점검 조건 문장을 `rules.KNOWN_CONDITIONS`에 적어 두고, 기준서에서 읽은 조건과 공백·줄바꿈·문장부호만 빼고 **정확히 같은지** 비교합니다. "이상→초과", "낮다→높다", "1월 1일→7월 1일"처럼 한두 글자로 뜻이 바뀌면 그 규칙은 "판단 보류"로 두고 평가 에이전트의 판단을 따릅니다. 최저임금 규칙만 금액과 기준 연도가 바뀌는 것을 허용합니다(값은 기준서의 최저임금 항목에서 읽습니다).
- **기준서 추출 결과 검증**: 기준서 PDF 원문에서 규칙 코드를 직접 읽어 추출 결과와 대조합니다. 규칙이 빠졌거나 중복되면 기준서 문제로 보고 등급을 내지 않습니다. 점검 조건·법령 근거·권장 행동은 원문 표를 글자 위치(칸의 가로 좌표)로 읽어, 추출 결과가 원문의 앞부분에서 잘린 것이 분명할 때만 원문으로 바로잡은 뒤 평가 입력 문서와 규칙 계산에 씁니다. 원문 판독이 더 짧거나 내용이 다르면 바꾸지 않아, 보정이 기준서 변경을 가리지 않습니다. 머리말·바닥글과 반복된 머리글은 건너뜁니다.
- **등급은 기준서가 정한다**: 최종 등급은 지적 카드(규칙 계산이 해당한다고 본 규칙 + 에이전트가 해당한다고 본 규칙)의 기준서 분류 중 가장 엄격한 것입니다. 에이전트가 근거 규칙보다 엄격하게 분류하면 남은 근거만큼만 따릅니다. 규칙 계산이 판단하지 못한 규칙이 있으면 그 규칙의 기준서 분류까지 에이전트 판단을 따르고, 규칙 코드 없이 적힌 지적은 '확인 필요'까지 올립니다. 확정된 지적보다 낮은 등급은 나오지 않습니다.
- **계산으로 확인한 통과는 의견 차이로**: 최저임금·다음 해 최저임금·휴게시간·주휴일·서명·교부처럼 계약서 숫자와 서명 값으로 통과가 정해지는 규칙을 에이전트가 지적하면, 등급에 넣지 않고 '의견 차이'로 근거와 함께 따로 보여 줍니다. 그 규칙에만 관한 에이전트 요청·누락 문장도 뺍니다. 값이 모호하면(금액·날짜·서명 값이 여러 개, 연장·갱신 조건, '또는'으로 적힌 휴게, 근무 시간 밖 휴게, 요일 없는 주휴일, 부정이 뒤따르는 교부 문구) 통과로 확정하지 않아 에이전트 지적이 카드로 남습니다. 위약금·필수 기재사항처럼 문장 해석이 필요한 규칙은 에이전트 지적을 그대로 등급에 넣습니다(놓치는 쪽이 더 해롭기 때문입니다).
- **판단 보류**: 규칙 계산이 판단하지 못한 규칙은 평가 에이전트의 판단을 따릅니다. 에이전트 분류도 없으면 "최소 ○○"로 표시하고 안심이라고 하지 않습니다.

`tests/test_rules.py`에 "기준서의 최저임금·규칙 분류를 바꾸면 결과가 바뀐다", "임계값을 바꾸면 코드는 판단을 보류한다"는 테스트가 있습니다.

### Studio에 반영한 것

팀 압축 파일의 설정을 학교 계정 Studio에 가져온 뒤 다음을 반영했습니다.

1. Review Agent의 Classify 노드 세 분류(safe, check_needed, risky) 설명을 기준서 참조형으로 바꿨습니다.
2. 세 Extract 노드 모두에 **`review_level`(String)** 항목을 맨 앞에 두고, 노드마다 자기 분류 값을 쓰게 했습니다(플레이북 HR 예시의 `match_level`과 같은 방식). 실제 응답에 Classify 결과가 따로 실리지 않아, 코드는 이 값으로 분류를 읽습니다.
3. Contract Agent의 `work_days` 설명에 "요일 없이 '주 5일 (요일은 협의)'처럼 일수만 적혀 있으면 그 문구를 그대로 한 항목으로 쓴다"를 넣었습니다. 그래야 1주 근로시간을 계산할 수 있습니다.
4. "워크플로우 설정 내보내기"로 받은 JSON으로 `agent_configs/`를 교체했고, "API로 이용하기" 화면의 Config ID를 `.env`의 `*_CONFIG_ID`에 넣었습니다.

## 실행

Python 3.12를 씁니다(`.python-version`, Railway도 같은 버전). 의존성 버전은 `requirements.txt`에 고정했습니다.

```bash
python -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env               # UPSTAGE_API_KEY와 Agent ID 3개를 채운다
```

```bash
python app.py --sample 3           # 콘솔에서 샘플 3 점검 (에이전트 3개 실제 호출)
streamlit run streamlit_app.py     # 화면 (http://localhost:8501)
```

`.env`가 비어 있으면 **데모 모드**로 열립니다. 업로드는 받지 않고 샘플 4종만 점검합니다. `fixtures/live/`에 실제 에이전트 결과가 있으면 그것을 재생하고("저장된 실행 결과 재생"), 없으면 팀 예상 추출값에 규칙 계산만 적용합니다("데모: 규칙 계산 결과").

### 발표용으로 실제 결과 저장하기

Upstage API 요청 제한에 걸려도 시연할 수 있게, 실제 에이전트 결과를 저장해 두고 재생할 수 있습니다.

```bash
for i in 1 2 3 4; do python app.py --sample $i --save-fixture; done   # fixtures/live/에 저장
```

이후 `FORCE_DEMO=1`이면 샘플은 저장된 실제 결과("저장된 실행 결과 재생"으로 표시)를 보여 줍니다.

### 테스트

```bash
pip install -r requirements-dev.txt
pytest
```

## 배포 (Railway)

플레이북 6장과 같습니다.

1. 이 폴더를 GitHub 저장소로 올립니다. `.env`는 `.gitignore`에 있어 올라가지 않습니다.
2. Railway → New → GitHub Repository → 저장소 선택.
3. Variables에 `.env`의 7개(`UPSTAGE_API_KEY`, `CONTRACT_AGENT_ID`, `CONTRACT_CONFIG_ID`, `CRITERIA_AGENT_ID`, `CRITERIA_CONFIG_ID`, `REVIEW_AGENT_ID`, `REVIEW_CONFIG_ID`)를 등록합니다. 발표 중 요청 제한이 걱정되면 `FORCE_DEMO=1`도 둡니다.
4. Start Command는 [`railway.json`](railway.json)에 들어 있습니다: `streamlit run streamlit_app.py --server.port=$PORT --server.address=0.0.0.0`
5. Settings → Networking → Generate Domain으로 공개 URL을 만듭니다.

3차에서 고친 것: 규칙 계산이 판단을 보류했는데 "교차 검증 일치"로 보이던 문제, '사용일 협의'·'(변경 없음)' 같은 정상 문구 오탐, "관계없이 교부"를 교부 거부로 읽던 문제, 세금·4대 보험 공제를 위약금으로 보던 문제, 근로자 요청 없는 4시간 휴게 예외, 에이전트 요약을 그대로 쓰던 최종 요약, 모든 항목이 빈 평가 결과, 제한 시간이 지난 뒤 SDK 재시도, 기준서 원문 코드 캐시.

2차에서 고친 것: 유사도 대신 정확 일치로 조건 비교, 기준서 원문 규칙 코드 대조, 확정 지적보다 낮은 등급과 모순된 요약 제거, '없음'·'미정'·'협의' 표기 처리, 4시간 휴게 예외, 배상 주체·부정 교부 문구, 불가능한 휴게시간·여러 근무 시각, 특약은 항상 표 밖 문단, 다음 해 최저임금 연도 표시, 빈 평가 결과 거부, Classify 실행 결과 우선, 폴링 남은 시간 제한, 기준서 추출 잠금.

1차에서 고친 것: 판단 보류가 안심으로 처리되던 경로, 시급 반올림으로 최저임금 미달이 통과하던 문제, 표의 빈 셀로 규칙이 어긋나던 문제, 부정 문맥("교부하지 않는다", "위약금을 금지한다") 오판, 등급만 올리고 요약·권장 행동이 그대로이던 문제, 긴 특약에서 PDF 생성 실패, HTTP 타임아웃, 캐시 키·원자적 저장, 손상·암호 PDF 검사, 의존성 버전 고정.
